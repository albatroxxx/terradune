GET STARTED

Install Terradune

Choose Docker for an image with Terraform included, or Go to use the Terraform CLI already on your machine. Both run the same local review interface.

Run with Docker

The image supports Linux AMD64 and ARM64, including Docker Desktop on Intel and Apple Silicon machines. Run these commands from your Terraform working directory in a POSIX shell.

# :latest follows the newest release; pin :1.0.1 for reproducibility.
IMAGE=ghcr.io/albatroxxx/terradune:latest

docker run --rm --user "$(id -u):$(id -g)" \
  -v "$PWD:/workspace" --entrypoint terraform \
  "$IMAGE" init -input=false

docker run --rm --user "$(id -u):$(id -g)" \
  --cap-drop ALL --security-opt no-new-privileges \
  --read-only --tmpfs /tmp:mode=1777 \
  -p 127.0.0.1:8383:8383 -v "$PWD:/workspace" \
  "$IMAGE"

Open localhost:8383. Stop the foreground container with Ctrl+C.

Initialize inside the container even if you already ran terraform init on the host. Linux providers are kept in .terradune/, separate from the host's .terraform/. Add .terradune/ to your workspace's .gitignore. The workspace mount must be writable for initialization and state locking.

The --user option avoids root-owned files on Linux. On Windows, use WSL2 for the commands above or use the Go installation. Docker Compose and advanced options are in the Docker guide.

Install with Go

Requires Go 1.27.1 or newer and Terraform on your PATH. Your provider version constraints, backend, and input variables still apply.

# @latest resolves the newest release; @v1.0.1 pins one.
go install github.com/albatroxxx/terradune@latest
terraform -chdir=./infra init
terradune ./infra

Make sure Go's binary directory is on your PATH. By default it is the bin directory under go env GOPATH. terradune -version prints the installed release.

AWS credentials

Terradune uses Terraform's provider authentication. For a local Go installation, keep your usual environment, AWS profile, and credential helpers.

For Docker, add the following options to both initialization and Terradune commands when using an AWS profile:

-e AWS_PROFILE -e AWS_REGION \
-v "$HOME/.aws:/home/terradune/.aws:ro"

Set AWS_PROFILE on the host first. For SSO, log in on the host before mounting the cache; a read-only mount cannot refresh it. The image does not include the AWS CLI or arbitrary credential_process helpers.

Alternatively, forward existing short-lived environment credentials with -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -e AWS_SESSION_TOKEN. Never put credential values in Docker build arguments or committed Compose files.

Review a plan

Resource Map is the default view. Pin a resource to trace its network path and direct associations. Plan lists each managed resource once per workspace. Graph shows dependencies, with arrows pointing from a dependent to its prerequisite.

Use search, action filters, and workspace scope to narrow the review. The expand control hides the header and filters without clearing the current selection. Open resource details to compare values and inspect related resources.

terradune -var-file prod.tfvars -var region=eu-west-2 ./infra

Docker accepts the same flags after the image name. Use container paths, such as -var-file /workspace/prod.tfvars /workspace. Publish a different host port with -p 127.0.0.1:8484:8383 when 8383 is occupied.

The v1 compatibility boundary

Supported in v1Not yet first-class
Managed resource changes, including unfamiliar AWS typesData-source inventory and read actions
Create, update, replace, destroy, unchangedImports, moves, forgotten resources, and output changes
Module addresses, count, for_each, multiple working directoriesDeferred plans and complete provider-alias account/region modeling
Unknown values and Terraform sensitivity masksAutomatic discovery of unmarked secrets

The Docker image includes Terraform 1.16.2. The graph suite also uses Terraform 1.14.4 fixtures. Other versions may work but are not a complete compatibility guarantee. Terraform decides whether your providers and configurations can be planned.

Keep it local

Terradune does not run terraform apply. Planning can still contact AWS, data sources, remote backends, and external programs referenced by your configuration. Only run trusted Terraform projects.

The application has no authentication or TLS termination. Keep Docker's published port bound to 127.0.0.1; do not expose it publicly. Sensitive values are masked using Terraform's metadata, but unmarked secrets and provider diagnostics still require care. Use synthetic plans in public screenshots.
